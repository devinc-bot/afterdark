# Plan de implementación — Perfil y configuración del dueño (+ settings de staff)

> Cómo se implementa esta feature. Complementa `spec.md`; no repetir criterios de aceptación.

## Orden de capas

```text
1. @afterdark/types      (SettingsResponse discriminado por role)
2. apps/api              (nuevo módulo settings, consolida owner)
3. apps/dashboard        (config/api.ts, modules/owner/ top-level, placeholder en modules/staff/, dispatcher en modules/settings/)
4. @afterdark/i18n       (namespace settings: owner.* / staff.*)
```

No hay cambios en `@afterdark/validators` ni en `packages/db` — se reutiliza `updateCurrentOwnerSchema` y las tablas existentes.

## Diseño técnico

- El dispatch de rol vive **en dos lugares intencionalmente**: API (`SettingsService`, resuelve por `payload.role` del JWT — para no exponer datos de un rol a otro) y dashboard (`SettingsView`, resuelve por el campo `role` que viene en la respuesta de `GET /settings`). No comparten lógica — son capas distintas.
- **`role` no viaja en `SessionResponse`/sesión del dashboard.** Se consideró agregarlo ahí, pero `apps/dashboard/app/modules/common/services/owner.service.ts` (`toSessionUser`) reconstruye `SessionResponse` a partir de un subconjunto de campos de owner después de cada guardado (optimistic update del store de sesión) — sin acceso a un `role` real en ese punto. En vez de forzar un valor, el rol se obtiene únicamente de `SettingsResponse` (`GET /settings`), que sí lo tiene siempre disponible en el backend.
- `OwnerService` no sobrevive como módulo aparte: al no tener otro consumidor, su lógica se movió dentro de `SettingsService` (pedido explícito del usuario durante la implementación) — evita una capa de indirección (`SettingsModule` → `OwnerModule` → `OwnerService`) que no aportaba nada una vez que `owner.controller.ts` desaparece.
- El endpoint `/settings` para `staff` en PATCH es un no-op defensivo (no lanza error, no persiste) porque el placeholder de dashboard nunca lo llama — evita levantar una excepción si alguien lo prueba manualmente, sin construir lógica real que no se pidió.
- El dashboard hace **un solo fetch** a `/settings` para decidir qué vista mostrar y, si es owner, alimentarla con los datos ya obtenidos — evita el doble fetch que hubiera resultado de "primero preguntar el rol, después pedir los datos".
- **Estructura de módulos del dashboard aplanada, pedido explícito del usuario tras la primera implementación.** En vez de anidar `owner`/`staff` dentro de `modules/settings/` (como se había implementado inicialmente), quedaron así:
  - `modules/owner/` — top-level. No colisiona con nada (no existía ya un módulo `owner`).
  - `modules/staff/` — el placeholder de settings de staff se sumó al módulo `staff` **ya existente** (gestión de personal del owner, feature 003-staff-invitations) como un componente más (`staff-settings-view.tsx`), en vez de crear un módulo separado.
  - `modules/settings/` — queda solo con el despachador (`components/settings-view.tsx`, `components/settings-load-states.tsx`) y el fetch compartido (`queries/use-settings.ts`, `services/settings.service.ts`).
  - Esto hace que `settings/components/settings-view.tsx` importe de `modules/owner` y `modules/staff` (módulos hermanos) — se aparta de la regla de `ARCHITECTURE.md` de no importar entre módulos hermanos, aceptado conscientemente por el usuario para tener una jerarquía más plana.

## Riesgos / edge cases

| Caso                                                                                                                           | Comportamiento esperado                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rol `admin`/`user` entra a `/settings`                                                                                         | `SettingsView` (dashboard) retorna `null` — pantalla en blanco. Sin guard en API tampoco. Fuera de alcance (ver Preguntas abiertas en `spec.md`).               |
| Staff llama `PATCH /settings` manualmente                                                                                      | `SettingsService` no-op: responde `{ role: 'staff' }` sin tocar DB.                                                                                             |
| Token JWT emitido antes del deploy sin lógica adicional de `role` (el campo siempre existió en `JwtPayload`)                   | No aplica — `role` ya viaja en todos los tokens actuales, el cambio es solo en `SessionResponse` (lectura), no en el JWT.                                       |
| Import roto tras aplanar `modules/settings/owner/` → `modules/owner/` y fusionar `modules/settings/staff/` en `modules/staff/` | Verificar con `pnpm type-check` en `dashboard` tras cada move; no debe quedar ningún `~/modules/settings-owner/...` ni `~/modules/settings-staff/...` residual. |

## Verificación manual

| Paso                                               | Resultado esperado                                                                                                             |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1. Login como owner, ir a `/settings`              | Se ve el formulario de perfil igual que hoy (nombre, DNI, CUIT/CUIL, etc.), guardar cambios funciona vía `PATCH /settings`.    |
| 2. Login como staff, ir a `/settings`              | Se ve `PageLayout` con título i18n + texto "Hello World", sin formulario, sin llamadas a API de perfil (chequear network tab). |
| 3. `GET /settings` con JWT de owner (curl/Postman) | Devuelve `CurrentOwnerResponse` completo, igual que antes `GET /owners/details`.                                               |
| 4. `GET /settings` con JWT de staff                | Devuelve `{ role: 'staff' }`.                                                                                                  |
| 5. `GET /session/me` con cualquier rol             | Incluye `role` en la respuesta.                                                                                                |
